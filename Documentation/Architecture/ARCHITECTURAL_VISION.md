# التصور المعماري المبدئي — UMS
**الإصدار:** 1.0 (مبدئي) — **التاريخ:** 17 نوفمبر 2026  
**الحالة:** تصور معماري قبل ERD المنطقي والفعلي. لا migrations بعد.

---

## 1. القرار المعماري الأساسي: Modular Monolith

نعتمد **Monolith بوحدات صريحة الحدود** في الإصدار الأول، للأسباب الموثقة في المخطط:
- القبول والدرجات والرسوم تحتاج معاملات متماسكة وقاعدة مركزية واحدة.
- تقليل التعقيد التشغيلي على فريق واحد وبيئة XAMPP محلية.
- لا ننتقل إلى Microservices إلا بحاجة مستقلة **مقاسة**.

لا يعني ذلك «كتلة فوضوية»: كل وحدة تملك جداولها ومنطقها، ولا تكتب مباشرة في جداول وحدة أخرى.

## 2. الحدود والوحدات (من الوثيقتين 3 و7)

```
app/Modules/
  Core/          إعدادات، تقويم، سياسات قابلة للإصدار
  Identity/      مستخدمون، أدوار، أذونات، نطاقات، تفويض، جلسات
  Organization/  أحرم، مبانٍ، طوابق، قاعات، كليات، أقسام، صيانة
  People/        دليل الأشخاص والمعرفات
  HR/            موظفون، هيئة تدريس، تعيينات، تكليفات
  Admissions/    دورات، طلبات، مستندات، مراجعات، قرارات
  Students/      ملف طالب، حالات، معادلات، وثائق
  Academics/     برامج، مشاركات، كتالوج، خطط وإصدارات
  Registration/  فترات، طرح، شعب، تسجيل
  Timetabling/   اجتماعات، قاعات، تعارضات
  Attendance/    جلسات وسجلات
  Assessment/    تقييمات، درجات، اعتماد، نشر
  Finance/       سياسات رسوم، فواتير، دفعات، إيصالات، رد، صناديق
  Documents/     وثائق، طلبات، مسارات موافقة
  Notifications/ إشعارات، إعلانات
  Reporting/     تقارير ولوحات
  Audit/         سجل تدقيق، أخطاء، نسخ، تكاملات
  (Postgraduate / Library / Integrations — مرحلية حسب الاعتماد)

app/Shared/{Audit,Documents,Exceptions,Support}
resources/views/{modules,components,layouts,lang}
database/{migrations,seeders,factories}
tests/{Unit,Feature,Browser}
```

قواعد العبور بين الوحدات: **Actions/Services + عقود صريحة + Events** للآثار الجانبية. لا استعلام مباشر من وحدة إلى جدول وحدة أخرى، ولا منطق أعمال في Blade/Livewire.

## 3. الطبقات الداخلية لكل وحدة

| الطبقة | المسؤولية |
|---|---|
| HTTP / Livewire | عرض، استقبال مدخلات، لا منطق أعمال |
| Form Requests | تحقق الخادم (المرجع) ورسائل عربية |
| Policies + Scope Queries | التفويض ونطاق السجل من جهة الخادم |
| Actions / Services | عمليات متعددة الخطوات داخل `DB::transaction` |
| Domain Models / Enums | قواعد الحالة والقيود |
| Events / Jobs | إشعارات وعمليات ثقيلة قابلة لإعادة المحاولة بلا مضاعفة |
| Migrations | مصدر المخطط الوحيد؛ لا تعديل يدوي في phpMyAdmin |

## 4. نموذج الأمان المعماري (Defense in Depth)

```
[Request] → Middleware(Auth) → Policy(Gate) → ScopeQuery(نطاق البيانات)
          → FormRequest(Validation) → Action(Transaction + Idempotency)
          → AuditLog(actor/action/entity/time/correlation/reason) → Response
```

- RBAC + نطاق: المؤسسة | الحرم | الكلية | القسم | البرنامج | الشعبة/المقرر | الذات.
- لا تجلب سجلات خارج النطاق ثم تخفيها في الواجهة.
- اختبار IDOR بتغيير المعرّف في URL/API إلزامي لكل وحدة.
- التصدير/الطباعة/البحث الجماعي يخضعان للنطاق نفسه.
- التفويض: بداية/نهاية/سبب/معتمد؛ لا تفويض ذاتي ولا توسيع لمحظور.
- انتهاء التكليف يُعيد تقييم الأدوار المرتبطة به.

## 5. فصل الأبعاد (القلب المفاهيمي)

| البعد | الكيانات | لا يتبع |
|---|---|---|
| الأكاديمي | كلية ← قسم ← برنامج ← خطة ← مقرر/شعبة | مدير الحرم |
| المكاني/التشغيلي | حرم ← مبنى ← طابق ← قاعة + صيانة | العميد (إدارياً) |
| التنظيمي | وحدات مركزية + تعيينات + مشرف تخصصي | — |
| الهوية | `person` ← `user` / `student` / `employee` | الدور ≠ النطاق |

العلاقات المتغيرة (`campus_college_assignments`, `employment_assignments`, `user_role_assignments`, `program_college_participations`, ...) تحمل `effective_from`/`effective_to`/`مرجع قرار`. **إغلاق سريان + فتح علاقة جديدة، لا حذف الماضي.**

## 7. العمليات الحرجة (Atomic + Idempotent)

1. **تحويل مقبول إلى طالب:** تحقق تكرار → شخص/طالب/برنامج/خطة/رقم داخل معاملة قابلة لإعادة المحاولة بأمان؛ معرف طلب القبول الأصلي محفوظ.
2. **التحصيل:** دفع + إيصال + تخصيص في transaction؛ مرجع الدفع الخارجي idempotent؛ فشل طباعة الإيصال لا يُلغي القبض.
3. **نشر النتائج:** اكتمال المراجعة → نسخة معتمدة/منشورة → إشعار؛ لا تغيير صامت.
4. **الجدولة:** قيد عدم تعارض قاعة/مدرس/شعبة على مستوى DB + تحقق التزامن؛ القاعة المعطلة لا تُحجز.

## 8. التكامل بين المجالات

| من → إلى | الحدث | الأثر |
|---|---|---|
| Admissions → Students | قرار قبول معتمد + استكمال شروط | إنشاء طالب واحد (idempotent) |
| Academics → Registration | خطة معتمدة + فترة مفتوحة | أهلية الشعب والمتطلبات |
| Registration → Timetabling | شعب وطرح | اجتماعات وحجوزات مع منع تعارض |
| Assessment → Students | نتيجة منشورة | سجل أكاديمي وكشف وفحص تخرج |
| Finance → Registration | استحقاق/تحصيل | **لا منع تلقائي إلا بقاعدة معتمدة**؛ سبب ومسار مراجعة |
| أي وحدة → Audit | عملية حساسة | سجل تدقيق + correlation id |
| أي وحدة → Notifications | حدث قابل للإشعار | إشعار داخلي أولاً؛ بريد/SMS بعد اعتماد مزود |

## 10. ما لا نفعله في الإصدار الأول
Multi-tenancy لعدة جامعات • Microservices بلا مبرر • قاعدة كتابة لكل حرم • LMS كامل • ERP تجاري • API لكل صفحة • تغييرات مخطط يدوية • سياسات أكاديمية/مالية مُخترعة.
