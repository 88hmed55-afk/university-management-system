## 1. ما نُفّذ

1. **ثماني جداول جديدة:** `service_request_types` / `service_requests` / `workflow_steps` / `request_events` / `notification_templates` / `notifications` / `delivery_attempts` / `announcements`؛ المفتاح العام لكل كيان فريد، والمرفقات تظل في قاعدة TASK-008 عبر الرابط morph `owner_type`/`owner_id` (لا تُخزَّن ملفات داخل MySQL، والملف تحت `private/` بـ checksum).
2. **الطلبات والمسارات:** نوع طلب يُعرَّف بمرجع قرار؛ مسار مُنسَّخ برقم إصدار وخطوات متسلسلة تحمل الدور ونطاق البيانات وشرط الانتقال. النشر يُثبِّت كل الخطوات ويمنع تعديلها؛ ونشر إصدار جديد أثناء وجود طلبات جارية يتطلب **مرجع ترحيل موثّقاً** (SCR-079).
3. **دورة حياة الطلب:** تقديم idempotent بمفتاح، وسجل أحداث `request_events` غير قابل للتعديل/الحذف لكل تقديم/تقدّم/إنجاز/رفض/إرجاع/سحب. الانتقال يتحقق من دور الفاعل ونطاقه، والرفض/الإرجاع يتطلبان سبباً، والسحب مسموح قبل المعالجة فقط وبسبب موثّق؛ لا حذف.
4. **قوالب وإشعارات:** قالب بإصدار (`code`+`version_no`) يمر `draft → approved → published` بفصل إنشاء عن اعتماد؛ الإرسال يأخذ العنوان/المحتوى/القناة من القالب المنشور كلقطة، ويُرسل إلى مستلم واحد مع تحقق من دوره النشط ونطاقه، والقناة الداخلية فقط لحين اعتماد مزود (P-021). تحديد المقروء مقصور على المستلم.
5. **محاولات الإرسال:** سجل append-only بمفتاح idempotency ورقم محاولة فريد لكل إشعار، مع رفض أي مزود خارجي قبل اعتماده وتسجيل سبب الفشل.
6. **الإعلانات:** إنشاء بمجهور (`audience_scope_code`) ونطاق اختياري ولغة `ar`/`en`، فصل إنشاء عن نشر، جدولة وتفعيل عند الموعد، وإيقاف بسبب موثّق؛ وبلا رابط إلى سجل subject كي لا تتسرب تفاصيل تتجاوز الصلاحية (SCR-006).
7. **`ServicesAccess` / `RequestAudit`:** تفويض مركزي للتهيئة/المعالجة/النشر/الإرسال، ومسجّل أحداث موحّد يكتب حدث الطلب والسجل العام داخل معامل الإجراء.
8. **ملفات ترجمة** عربية/إنجليزية للحالات والقنوات والأحداث + 8 مصانع + 8 اختبارات Feature.

> لا لوائح خدمات أو أسباب محددة أو قوالب رسمية أو مزودي رسائل مُفترضة؛ كل قيمة يُدخلها المخول صراحةً (P-018/P-021/P-022/P-023).
