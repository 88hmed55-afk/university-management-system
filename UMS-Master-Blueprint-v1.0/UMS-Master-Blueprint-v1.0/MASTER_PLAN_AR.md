# 1. الرؤية والميثاق والنطاق والحوكمة

## الرؤية
نظام معلومات موحد لإدارة جامعة أهلية خاصة واحدة في صنعاء، متعددة الأحرم، يبدأ قبل أول دفعة، ويستوعب 1,000–5,000 طالب مبدئياً، مع مسارات البكالوريوس والماجستير والدكتوراه. الهدف تشغيل الجامعة من مصدر بيانات واحد، مع صلاحيات مؤسسية واضحة وسجل تاريخي موثوق.

## أهداف العمل
1. توحيد بيانات الأشخاص والمتقدمين والطلاب والموظفين والبرامج والمقررات.
2. إدارة دورة الطالب من التقديم حتى التخرج والوثائق.
3. توحيد السياسات المركزية مع تفويض التشغيل المحلي للأحرم.
4. الاحتفاظ بتاريخ الخطط والرسوم والنتائج والقرارات.
5. تقليل الإدخال المتكرر والأخطاء اليدوية والتعارضات.
6. تقديم تقارير موثوقة للإدارة العليا والكليات والأقسام والأحرم.
7. تأسيس كود آمن قابل للصيانة والنقل من جهاز المطور إلى خادم الجامعة.

## النطاق المعتمد
- مؤسسة واحدة متعددة الأحرم، وليست شبكة جامعات مستقلة في الإصدار الأول.
- الإدارة المركزية تضع السياسات وتعتمد القرارات ضمن صلاحياتها.
- مدير كل حرم مسؤول عن موظفي التشغيل والخدمات والأعمال اليومية في حرمه ضمن تفويض، ويتبع الإدارة المركزية إدارياً.
- لكل كلية عميد مستقل يتبع المسار الأكاديمي/الإداري المركزي، ولا يتبع مدير الحرم.
- لكل قسم رئيس أكاديمي يتبع عميد الكلية.
- الكلية قد تعمل في أكثر من حرم، والحرم قد يستضيف أكثر من كلية.
- لكل برنامج كلية رئيسية مسؤولة، ويمكن مشاركة كليات أخرى في تقديمه.
- كتالوج المقررات مركزي؛ المقرر الواحد يمكن استخدامه في عدة خطط.
- قاعدة تشغيل مركزية موحدة؛ لا قواعد كتابة مستقلة لكل حرم.

## النطاق الوظيفي
**إطلاق أساسي:** النواة والهيكل، الهوية والصلاحيات، الأحرم والمرافق، القبول، الطلاب، البرامج والخطط والمقررات، التسجيل، الجداول، الحضور، الاختبارات والنتائج، الرسوم والتحصيل، الطلبات والوثائق، الإشعارات، التقارير، التدقيق والنسخ الاحتياطي.

**إطلاق مرحلي/لاحق حسب اعتماد الجامعة:** سير الدراسات العليا والرسائل، المكتبة، المحاسبة العامة الكاملة، المشتريات والموردون والأصول والرواتب، بوابة الخريجين، تكامل LMS، تطبيق جوال أصلي، بوابات الدفع والرسائل النصية.

**خارج نطاق الإصدار الأول:** Multi-Tenancy لعدة جامعات، Microservices بلا مبرر، قاعدة بيانات مستقلة قابلة للكتابة لكل حرم، LMS كامل، نظام ERP تجاري شامل غير مرتبط باحتياجات الجامعة.

## مبادئ لا يجوز كسرها
- مصدر حقيقة واحد لكل مفهوم مؤسسي.
- الشخص منفصل عن حساب الدخول، والدور منفصل عن نطاق البيانات.
- الموقع الجغرافي منفصل عن الكلية والقسم والبرنامج.
- الخطط والسياسات والرسوم قابلة للإصدار والتأريخ عند الحاجة.
- تغيير سياسة مستقبلية لا يغير أثرها التاريخي تلقائياً.
- لا حذف صامت لدرجات أو مدفوعات أو قرارات معتمدة؛ التصحيح بإجراء موثق.
- تفويض وصلاحيات محددة؛ كلمة «مدير» لا تعني وصولاً شاملاً.
- كل عملية حساسة لها صاحب وسبب ووقت وسجل تدقيق.
- العربية RTL هي الأساس مع دعم الإنجليزية.
- Modular Monolith كبداية؛ فصل الخدمات فقط بعد مبرر مقاس.

## مؤشرات النجاح
- رحلة قبول كاملة دون تكرار سجل الشخص أو الطالب.
- إضافة حرم/كلية/قسم/برنامج من الواجهة دون تعديل الكود ضمن السياسات المعتمدة.
- دعم خطتين دراسيتين للبرنامج نفسه على دفعات مختلفة.
- منع الوصول الأفقي بين الأحرم والكليات خارج الصلاحية.
- منع تعارض القاعات والمدرسين والشعب.
- تطابق التقارير مع سجلات المصدر.
- نجاح اختبار استعادة نسخة احتياطية.
- لا عيوب أمنية حرجة/عالية قبل الإطلاق.
- اجتياز UAT واختبار الحمل المعتمد.

## الحوكمة وإدارة التغيير
أي تغيير يمر بطلب برقم، سبب ومالك، تحليل أثر على الإجراءات والبيانات والتقارير والصلاحيات والاختبارات، موافقة صاحب السياسة، تحديث الوثائق/ERD، تنفيذ بفرع Git، مراجعة كود، اختبار انحداري، واعتماد إصدار. لا يحول المطور قراراً شفهياً إلى قاعدة نظام دائمة.

# 2. النموذج التنظيمي والأكاديمي والمكاني

## أبعاد السلطة
1. **مركزي:** رئاسة الجامعة والإدارات المركزية تضع السياسات وتصدر الاعتمادات وفق اللوائح.
2. **أكاديمي:** الإدارة الأكاديمية ← العمداء ← رؤساء الأقسام ← أعضاء هيئة التدريس، مع لجان البرامج والمجالس التي تعتمدها الجامعة.
3. **تشغيلي مكاني:** الإدارة المركزية ← مديرو الأحرم ← موظفو التشغيل والخدمات والمرافق المحلية ضمن التفويض.

مدير الحرم ليس رئيساً أكاديمياً للعمداء؛ والعميد لا يدير تلقائياً كل مرفق مشترك. يتعاون المساران ولا يندمجان.

## الكيانات
- الجامعة: مؤسسة واحدة.
- الوحدات المركزية: رئاسة، نيابات، إدارات، عمادات مساندة حسب الهيكل الرسمي.
- الكليات: كيانات أكاديمية/تنظيمية.
- الأقسام: تتبع كلية واحدة إدارياً في كل فترة سريان.
- الأحرم: مواقع جغرافية وتشغيلية.
- المباني والطوابق والقاعات والمعامل: موارد مكانية.
- البرامج: لها كلية أكاديمية رئيسية واحدة، مع دعم كليات مشاركة.
- المقررات: كتالوج مركزي، وقد يدرسها أكثر من برنامج وقسم.

## توزيع المسؤوليات
| المنصب | مسؤول | غير مخول تلقائياً |
|---|---|---|
| رئيس الجامعة | توجيه واعتمادات عليا وفق اللائحة | تجاوز الضوابط المالية/الأكاديمية |
| الإدارة الأكاديمية | سياسات ومراجعات واعتمادات أكاديمية | إدارة الخادم أو التحصيل |
| العميد | إدارة الكلية أكاديمياً وإدارياً ضمن التفويض | تغيير سياسة الجامعة منفرداً |
| رئيس القسم | تنظيم التدريس والمقررات والتوصيات | اعتماد خطة أو برنامج جديد منفرداً |
| مدير الحرم | تشغيل الموقع والموظفين التشغيليين والمرافق | تغيير نتائج أو خطط أو رسوم أو قرارات العمداء |
| المالية | الرسوم والتحصيل والمطابقة | تعديل سجل أكاديمي |
| تقنية المعلومات | الحسابات والمنصة والأمن | اعتماد قبول/درجة بصفته التقنية |

## التبعية الوظيفية
لكل تكليف وظيفي: مدير إداري مباشر واحد، مشرف تخصصي إن وجد، الوحدة/الكلية/القسم، الحرم أو مواقع العمل، تاريخ بدء ونهاية، نوع التكليف، صاحب قرار التعيين. يسمح بإشراف تخصصي موازٍ لكن لا بتبعية إدارية مباشرة متضاربة.

## البرامج المشتركة
- كل برنامج يسجل مرة واحدة وله كلية رئيسية مسؤولة.
- الكليات الأخرى ترتبط بعلاقة مشاركة مؤرخة تحدد نوع المساهمة والمسؤولية.
- منسق البرنامج ولجنة البرنامج يحددان بقرار جامعي.
- السجل الأكاديمي والقبول والتخرج يظلان تحت برنامج واحد.

## المقرر والخطة والشعبة
- `courses`: تعريف المقرر المركزي، رمزه ووصفه وقسمه المالك.
- `course_versions`: نسخ توصيف المقرر ومخرجاته ومحتواه.
- `study_plan_versions`: نسخ الخطة التي تعتمد على مقررات الكتالوج.
- `course_offerings`: طرح مقرر في فصل دراسي.
- `course_sections`: الشعب الفعلية.
- `section_meetings`: زمن ومكان المحاضرات.
- `teaching_assignments`: المدرسون المسندون للشعبة.
- `course_enrollments`: تسجيل الطلاب في الشعب.

لا تكرر المقرر لأنه مستخدم في خطة أخرى. لا تخلط تعريف المقرر بالشعبة التي تدرس فعلياً.

## الخطط وإصداراتها
لكل إصدار خطة: رقم، تاريخ اعتماد، تاريخ سريان، حالة، الساعات/الوحدات، المقررات، المتطلبات، الاختيارات، ومتطلبات التخرج. الطالب مرتبط بإصدار محدد. إصدار خطة جديدة لا ينقل الطلاب تلقائياً؛ الانتقال يحتاج قراراً موثقاً وتحليل أثر.

## العلاقات المكانية
الحرم يحتوي مباني، المبنى يحتوي طوابق، والطابق يحتوي قاعات ومعامل. الكلية ترتبط بأكثر من حرم عند الحاجة بعلاقة مؤرخة. القاعة قد تستخدمها عدة كليات عبر نظام الجدولة. مكان المحاضرة يحدد على مستوى اجتماع الشعبة وليس تعريف المقرر.

## أثر الزمن
العلاقات القابلة للتغيير تحفظ `effective_from` و`effective_to` ومرجع قرار. لا تحذف علاقة قديمة لمجرد تغيير مدير أو كلية أو حرم؛ أغلق سريانها وافتح العلاقة الجديدة.

## دورة القبول
1. إنشاء دورة قبول واعتمادها وفتح البرامج المتاحة.
2. المتقدم ينشئ حساباً ويعبئ البيانات ويختار رغباته.
3. يرفع المستندات ويرى النواقص.
4. مراجعة إدارية ثم أكاديمية/اختبار/مقابلة إذا نصت السياسة.
5. توصية ثم قرار معتمد (قبول/رفض/انتظار/مشروط إن اعتمد).
6. إشعار المتقدم واستكمال المتطلبات.
7. التحقق من الهوية ومنع التكرار.
8. تحويل المقبول إلى سجل طالب واحد مع الرقم والبرنامج والدفعة وإصدار الخطة.
9. إنشاء استحقاق مالي وتفعيل الخدمات حسب شروط الجامعة.

حالات استثنائية يجب اختبارها: طلب ناقص، تكرار تقديم، تغيير رغبة، عدم قبول العرض، تأجيل القبول، مستند مشكوك، فشل الشبكة أثناء الإرسال.

## دورة التسجيل
- فتح فترة التسجيل وقواعدها.
- تحديد أهلية الطالب وحالته وخطته.
- عرض الشعب المسموح بها بحسب المتطلبات السابقة والسعة والتعارض.
- تسجيل الطالب ثم الإضافة/الحذف/الانسحاب ضمن النافذة.
- إقفال التسجيل وإصدار قوائم نهائية.
- حفظ ما ينطبق على الفترة من خطة ومقرر وشعبة ورسوم وسياسة.

لا تمنع المالية التسجيل تلقائياً إلا بقاعدة معتمدة، ويجب أن يظهر سبب المنع ومسار المراجعة.

## الجدولة والموارد
تحديد الفترات والأيام، طرح المقررات، إنشاء الشعب، إسناد المدرسين، اختيار قاعات ملائمة، إدخال الاجتماعات، كشف تعارضات القاعة والمدرس والشعبة، النشر والإشعار، وحفظ تاريخ أي تغيير.

## الحضور والنتائج
جلسات حضور، حالات حضور/غياب/تأخر/عذر، قفل الإدخال، تقييمات وأوزان معتمدة، إدخال الدرجات، مراجعة واعتماد ونشر، اعتراضات وتعديل موثق، كشف درجات وفحص تخرج. لا تعديل صامت لنتيجة منشورة.

## الرسوم والتحصيل
تعريف رسوم ذات إصدارات وتواريخ، إنشاء استحقاقات وفواتير، تسجيل دفعات وإيصالات، تخصيص المبالغ، كشف حساب، رد/عكس/تسوية، إقفال صندوق ومطابقة. الأموال `DECIMAL` مع رمز العملة. العملات وأسعار الصرف والخصومات والضرائب تنتظر اعتماد المالية.

## الموارد البشرية
ملف موظف، تعيينات وتكليفات، تبعية إدارية ومشرف تخصصي، ملفات أعضاء هيئة التدريس، تكليفات التدريس، ثم الإجازات والدوام والتقييم عند اعتماد السياسات. مدير الحرم لا يغير التعيين أو الراتب دون تفويض.

## الدراسات العليا
قبول الماجستير والدكتوراه، ملف بحث، مشرف رئيسي ومشاركون، لجنة، مقترح وإصدارات، مراحل تقدم وتقارير، امتحان تأهيلي عند اعتماده، مناقشة ومحضر وقرار، وإيداع النسخة النهائية. لا تفرض هذه الحقول على طلاب البكالوريوس.

## المكتبة
فهرس ونسخ ومواقع، عضويات، إعارة وإرجاع وتجديد وحجز، غرامات فقط إن اعتمدت، وجرد ومفقود/تالف.

## الوثائق والطلبات والإشعارات
كل طلب له نوع ومقدم وحالة ومرفقات ومسؤول ومسار اعتماد وقرار. الوثيقة لها رقم ونوع ومالك وتاريخ وسرية وإصدارات. الإشعارات داخل النظام أساساً ثم البريد/SMS بعد اعتماد مزود، ولا تضع بيانات حساسة في رسائل عامة.

## التكاملات
بوابة دفع، SMTP، SMS، LMS، أو خدمة تحقق فقط عند توفر API موثوق وموافقة الجامعة. كل تكامل له أسرار خارج الكود، سجل طلبات، إعادة محاولة آمنة، ومنع تكرار العمليات.

# 4. جرد صفحات النظام — وصف تفصيلي لكل شاشة

هذه قائمة التصميم الوظيفي للواجهات. قبل التنفيذ قد تدمج صفحات أو تفصلها بناءً على اختبار تجربة المستخدم، لكن لا تحذف وظيفة أو قاعدة عمل دون تحديث سجل المتطلبات. كل صفحة تتبع قالباً موحداً: هدف، معلومات، إجراءات، صلاحيات، تحقق، حالات واجهة، وتدقيق.

## القواعد المشتركة
- كل قائمة بها بحث وفلاتر وفرز وترقيم صفحات وحالة فارغة ورسالة خطأ واضحة.
- كل نموذج يظهر الإلزامية، الوصف، حدود المدخلات، رسائل التحقق، ويحافظ على القيم عند الفشل.
- الإجراء الحساس يعرض أثره ومرجعه قبل التنفيذ؛ لا حذف صامت للسجلات التاريخية.
- صلاحيات الخادم هي المرجع؛ إخفاء الزر وحده ليس حماية.
- كل تنزيل/تصدير يخضع لنطاق الصلاحية نفسه المطبق على الصفحة.
- اتجاه RTL أصلي؛ الأكواد والأرقام والبريد تعزل كـ LTR عند الحاجة.
- كل شاشة تعالج التحميل والفراغ وعدم وجود نتائج وفشل الشبكة وعدم الصلاحية وانتهاء الجلسة.

# 5. الأدوار والصلاحيات ونطاق الوصول

## النموذج
يعتمد RBAC (دور + أذونات) مع نطاق بيانات وسياق العملية. النطاقات الممكنة: المؤسسة، الحرم، الكلية، القسم، البرنامج، الشعبة/المقرر، والذات (الطالب أو المستخدم نفسه). وقد تستخدم شروط إضافية مثل أن التسجيل مفتوح، أو المعاملة في حالة قابلة للاعتماد، أو التفويض ساري المفعول. الدور وحده لا يفتح جميع السجلات.

## فصل المهام (SoD)
- منشئ سياسة الرسوم لا يعتمدها وحده إذا تتطلب الرقابة فصل مهام.
- أمين الصندوق لا يمحو إيصالاً؛ الرد/العكس يحتاج مراجعة واعتماداً.
- المدرس يدخل الدرجة؛ المعتمد يراجع وينشر وفق اللائحة.
- مدير النظام التقني لا يمنح نفسه اعتماداً مالياً أو أكاديمياً.
- مدخل قرار القبول لا يعتمد وحده إذا نصت اللائحة على لجنة.

## التنفيذ الأمني
- التحقق عبر Middleware + Policies/Gates + نطاقات الاستعلام.
- لا تجلب سجلات خارج النطاق ثم تخفيها في الواجهة.
- اختبار IDOR بتغيير معرف السجل في URL/API.
- السجلات الجماعية والتصدير والطباعة تخضع لنفس النطاق.
- التفويض له بداية ونهاية وسبب ومعتمد، ولا يسمح بالتفويض الذاتي أو توسيع صلاحية محظورة.
- انتهاء تكليف الموظف يعيد تقييم/ينهي الأدوار المرتبطة بالتكليف.
- مراجعة دورية للصلاحيات وإقرار من مالك الوحدة.

# 6. نموذج البيانات وقاموس الكيانات

## قواعد عامة
- InnoDB، ترميز `utf8mb4`، وتجربة Collation على بحث عربي فعلي قبل اعتماده.
- مفاتيح داخلية موحدة (`BIGINT` أو ULID وفق قرار واحد)، مع معرف عام غير متسلسل للروابط التي تظهر خارج النظام عند الحاجة. الرقم الجامعي/الوظيفي رمز عمل وليس مفتاحاً أساسياً.
- أسماء الجداول والأعمدة `snake_case`، والقيم المرجعية المترجمة في ملفات اللغة.
- FK وUnique وIndexes إلزامية حسب العلاقات؛ لا تعتمد على التحقق الأمامي وحده.
- أموال `DECIMAL` مع رمز العملة؛ لا FLOAT/DOUBLE.
- تخزين التوقيت موحد وعرضه حسب منطقة الجامعة.
- لا تخزن ملفات الطالب داخل MySQL؛ خزّن metadata في DB والملف في private storage.
- لا تضع JSON بديلاً عن علاقة تحتاج بحثاً أو تقارير أو قيداً.
- لا soft-delete تلقائي للعمليات الأكاديمية والمالية؛ استخدم الحالة/الأرشفة والعكس.

## قيود أساسية
- رقم الطالب ورقم الموظف لا يعاد استخدامهما.
- البرنامج له كلية رئيسية واحدة، وله مشاركات متعددة ممكنة.
- القسم يتبع كلية واحدة في فترة سريان.
- المقرر المركزي لا ينسخ لكل برنامج.
- لا تسجيلين نشطين للطالب في الشعبة نفسها.
- لا حجز متعارض لقاعة/مدرس في الزمن نفسه؛ اختبر القيود والتزامن.
- لا تنشر درجات غير معتمدة ولا تتجاوز حدود عناصر التقييم.
- أرقام الفواتير والإيصالات فريدة ولا يعاد استخدام الملغى.
- كل حركة رد/عكس ترتبط بالحركة الأصلية.
- كل ملف له checksum وmetadata وصلاحية تنزيل.

| Git | GitHub/GitLab أو مستودع خاص | مراجعة PR وCI |
| Tests | PHPUnit أو Pest المتوافق + Feature/E2E | اختر مساراً أساسياً واحداً |

الإصدارات تتحقق عند إنشاء التطبيق. إذا كان PHP في XAMPP أقل من 8.3، فلا تبدأ Laravel 13 حتى تجهز PHP متوافقاً. لا تفترض أن نسخة XAMPP لديك ملائمة قبل الفحص.

## لماذا Modular Monolith؟
النظام في الإصدار الأول يحتاج معاملات متماسكة للقبول والدرجات والرسوم وقاعدة مركزية. Modular Monolith يقلل التعقيد التشغيلي ويحافظ على حدود واضحة. لا ننتقل إلى Microservices إلا عند وجود حاجة مستقلة مقاسة.

## الوحدات البرمجية
Core، Identity، Organization، People، HR، Admissions، Students، Academics، Registration، Timetabling، Attendance، Assessment، Finance، Documents، Workflow، Notifications، Postgraduate، Library، Reporting، Audit، Integrations.

## هيكل مجلدات مقترح
```text
app/Modules/{Admissions,Academics,Students,Finance,Organization,Identity}/
  Actions/ DTOs/ Enums/ Events/ Jobs/ Models/ Policies/ Queries/ Services/ Http/
app/Shared/{Audit,Documents,Exceptions,Support}/
resources/views/{modules,components,layouts,lang}/
database/{migrations,seeders,factories}/
tests/{Unit,Feature,Browser}/
docs/
```
كل وحدة تملك قواعدها؛ لا تكتب وحدة مباشرة في جداول أخرى. استخدم Actions/Services وعقود تكامل واضحة.

## قواعد الكود
- Controllers رفيعة؛ Form Requests للتحقق.
- Policies/Gates للتحكم بالوصول ونطاق السجل.
- Actions/Services للعمليات متعددة الخطوات.
- DB Transactions للعمليات الذرية.
- Events/Listeners للإشعارات والآثار الجانبية لا لإخفاء منطق أساسي.
- Jobs للعمليات الثقيلة؛ يجب أن تكون قابلة لإعادة المحاولة بلا مضاعفة.
- Queue قاعدة بيانات للتطوير، وRedis أو backend آخر في الإنتاج إذا برره الحمل.
- API فقط للتكاملات والبوابات التي تحتاجه؛ لا تنشئ API لكل صفحة.
- Migrations هي مصدر مخطط قاعدة البيانات؛ لا تعدل الإنتاج يدوياً من phpMyAdmin.

## عمليات حساسة
**تحويل متقدم إلى طالب:** التحقق من التكرار، إنشاء/ربط الشخص والطالب والبرنامج والخطة والرقم الجامعي في معاملة قابلة لإعادة المحاولة بأمان.

**التحصيل:** حركة دفع وإيصال وتخصيص داخل transaction؛ مرجع الدفع الخارجي idempotent؛ فشل طباعة الإيصال لا يلغي القبض.

**نشر النتائج:** التأكد من اكتمال المراجعة، إنشاء نسخة معتمدة/منشورة وإشعار، وعدم تغيير نتيجة منشورة صامتاً.

## إعداد Windows/XAMPP
1. شغّل MySQL فقط من XAMPP إذا ستستخدمه كقاعدة محلية.
2. افحص `php -v` و`where.exe php` وComposer وNode/NPM.
3. نفذ `SELECT VERSION();` لمعرفة MySQL.
4. تأكد أن PHP CLI هو نفس إصدار PHP المستخدم لتشغيل Laravel.
5. أنشئ قاعدة بيانات فارغة ومستخدم تطبيق مخصصاً؛ لا تستخدم root بلا كلمة مرور إلا في مختبر مؤقت.
6. أنشئ مشروع Laravel واختر Livewire starter kit؛ أنشئ `.env` ومفتاح التطبيق ثم نفذ migrations والاختبارات.
7. استخدم `php artisan serve` و`npm run dev` محلياً؛ لا يلزم نقل المشروع إلى `htdocs` مع خادم Laravel المحلي.
8. بيانات التطوير اصطناعية فقط.

## Git وCI
- `main` للإصدارات المعتمدة؛ feature branch لكل مهمة؛ Pull Request ومراجعة.
- امنع رفع `.env` والأسرار والنسخ الاحتياطية وبيانات الطلاب.
- CI: تثبيت dependencies من lock files، تنسيق الكود، اختبارات، build للواجهة.
- migrations وseeders وبيانات تجريبية موثقة.

# 8. تصميم الواجهة وتجربة الاستخدام العربية RTL

## التوجه البصري
واجهة مؤسسية هادئة وعملية. لا تفرط في البطاقات والتدرجات والظلال. الأولوية لسهولة إنجاز العمل، وضوح الحالة، وتجنب الخطأ. العربية RTL هي الاتجاه الافتراضي والإنجليزية مدعومة.

## التخطيط العام
- شريط جانبي قابل للطي للتنقل حسب الصلاحيات.
- شريط علوي للسياق (الحرم/الفترة عند الحاجة)، البحث، الإشعارات، الملف الشخصي.
- مساحة محتوى بعنوان واضح ومسار تنقل.
- صفحات القوائم تستخدم جداول بحث وفرز وفلاتر وترقيم.
- صفحات التفاصيل تستخدم تبويبات بحسب صلاحيات المستخدم.
- النماذج الطويلة تقسم إلى مجموعات أو معالج خطوات.
- شاشة الاعتماد تعرض ملخص القرار والأثر قبل الإجراء.

## مكونات مشتركة
Button variants، DataTable، Search/Filter bar، FormField، StatusBadge، ConfirmDialog، Timeline، FileUploader، AuditPanel، PermissionNotice، EmptyState، LoadingState، ErrorState، PrintHeader.

## قواعد RTL
- خصائص CSS المنطقية بدلاً من left/right.
- لا تعكس كل الأيقونات؛ اعكس اتجاه التنقل حيث يلزم.
- الأكواد والأرقام الجامعية والبريد تعرض LTR داخل حاويات منعزلة.
- اختبر حقول الهاتف والأرقام المختلطة والنسخ واللصق.
- الترويسات والنماذج والجداول والطباعة يجب أن تكون RTL حقيقياً، لا مجرد محاذاة يمين.

## قواعد النماذج
- تسمية واضحة وتعليمات مختصرة وإلزامية ظاهرة.
- لا تفقد القيم بعد خطأ التحقق.
- القوائم المترابطة (كلية ← قسم ← برنامج) لا تعرض عناصر غير مسموح بها.
- تحقق الخادم هو المرجع، والتحقق الأمامي مساعد فقط.
- الأزرار تسمي الإجراء بدقة: «إرسال للمراجعة» لا «حفظ» عندما تتغير الحالة.

## تجربة كل دور
- مدير الحرم يرى تشغيل الحرم والمرافق ومهام الموظفين التشغيليين.
- العميد يرى الكلية وأقسامها وبرامجها وقراراتها الأكاديمية المصرح بها.
- رئيس القسم يرى الشعب والمدرسين والنتائج الأولية.
- القبول يرى الطلبات والمرفقات والنواقص.
- المالية ترى الفواتير والمدفوعات والمطابقة.
- الطالب يرى التسجيل والجدول والنتائج المعتمدة والطلبات وحسابه فقط.
- المدرس يرى الشعب المسندة إليه ومهامه الأكاديمية فقط.

## حالات الواجهة
كل شاشة يجب أن تعالج: التحميل، الفراغ، لا نتائج، خطأ الخادم، عدم الصلاحية، انتهاء الجلسة، فشل رفع ملف، تعارض، نجاح الحفظ، انقطاع الشبكة، تكرار الإرسال.

## الطباعة والتصدير
قوالب رسمية ثابتة للشهادة والإفادة وكشف الدرجات والإيصال؛ شعار ورقم وثيقة وتاريخ واعتماد حسب القالب. دعم خط عربي في PDF. لا يتجاوز التصدير نطاق صلاحية الصفحة، ويسجل تصدير البيانات الحساسة.

# 9. الأمن والخصوصية وسجل التدقيق

## مبادئ
أقل صلاحية، عدم الثقة بمدخلات المتصفح، تصنيف البيانات، فصل البيئات، تشفير النقل والنسخ، سجل تدقيق، مراجعة أمنية قبل الإطلاق. هذه ضوابط هندسية ولا تشكل وحدها شهادة امتثال قانوني.

## المصادقة
- حساب مستقل لكل مستخدم؛ يمنع الحساب المشترك.
- تخزين كلمات المرور عبر hashing آمن، لا تخزين قابل للعكس.
- MFA إلزامي للحسابات الحساسة ومستحسن للموظفين.
- Rate limiting لمحاولات الدخول واستعادة الحساب.
- لا تسجيل موظفين عاماً؛ إنشاء الحسابات من مسؤول أو دعوة. المتقدم له بوابة منفصلة.
- إنهاء الجلسات عند تعطيل الحساب أو تغيير بيانات أمنية حرجة.

## التفويض
- Middleware للمصادقة + Policies/Gates + Scope-aware queries.
- لا تعتمد على إخفاء الأزرار.
- لا تقبل معرف طالب/حرم/كلية من المتصفح دون تحقق.
- اختبار IDOR وتجاوز الدور والنطاق في كل وحدة.
- التصدير والطباعة والبحث الجماعي تخضع لنفس الأذونات.
- التفويض المؤقت له بداية ونهاية وسبب ومعتمد ولا يتجاوز الصلاحيات المحظورة.

## حماية التطبيق والملفات
- HTTPS في التشغيل المتصل.
- CSRF وescaping ضد XSS، واستعلامات مهيأة ضد SQL injection.
- رفع الملفات بقائمة أنواع وأحجام مسموحة وفحص MIME الفعلي، تخزين خارج public، اسم عشوائي، وفحص malware عند توفره.
- أسرار API خارج Git، وتدويرها، ولا تعرض مرة أخرى بعد الحفظ.
- تعطيل Debug في الإنتاج وإخفاء stack traces.
- Security headers/CSP بعد اختبار عدم كسر الواجهة.

## تصنيف بيانات أولي
| التصنيف | أمثلة | الضوابط |
|---|---|---|
| عام | أخبار وبرامج منشورة | نشر معتمد |
| داخلي | إجراءات وتقارير تشغيلية | مستخدمون مصرحون |
| سري | سجلات الطلاب والموظفين والدرجات والرسوم | صلاحيات دقيقة وتدقيق |
| شديد الحساسية | معرفات رسمية وشكاوى وملفات سرية | أقل عدد من المخولين وتسجيل الوصول |

الجامعة والمستشار القانوني يحددان التصنيف النهائي وقواعد الاحتفاظ.

## سجل التدقيق
يسجل actor، الفعل، نوع ومعرف السجل، الوقت، النتيجة، correlation ID، السبب، والقيم السابقة/الجديدة للحقول الحساسة عند ملاءمتها. لا يسجل كلمة مرور أو token أو سر تكامل. العمليات ذات الأولوية: الدخول، تغيير الأدوار، التفويض، اعتماد/رفض، تغيير نتيجة، قبض/رد، تغيير رسوم، إصدار وثيقة، تصدير حساس، استعادة.

## الخصوصية والاحتفاظ
- اجمع أقل قدر لازم من البيانات، ووثق غرض الحقل.
- فصل بيانات الاتصال عن السجل الأكاديمي عند الحاجة.
- لا تستخدم بيانات حقيقية في بيئة التطوير أو Git.
- سياسة الاحتفاظ/الأرشفة/الإتلاف تعتمد من الجامعة ومستشارها القانوني.
- تصحيح البيانات يكون عبر إجراء موثق لا حذفاً عشوائياً.

## إدارة الحوادث
اكتشاف → تصنيف → احتواء دون إتلاف الأدلة → حفظ السجلات → إصلاح السبب → استعادة آمنة → توثيق السبب الجذري → إخطار الجهات المعنية وفق سياسة الجامعة والمتطلبات القانونية.

## النسخ والاستعادة
نسخ مشفرة خارج الخادم الأساسي، نسخ ملفات الوثائق متزامنة مع قاعدة البيانات، اختبار استعادة دوري، وتحديد RPO/RTO مع الجامعة بعد اختبار عملي لا بالتخمين.

# 10. التقارير ولوحات المعلومات

كل تقرير له مالك، وتعريف للمؤشر، ومصدر بيانات، وفلاتر، ونطاق صلاحية، وتاريخ تحديث. يجب بيان ما إذا كانت الأرقام لحظية أو دورية، وفصل المسودات عن السجلات المعتمدة.

## لوحات الدور
| الدور | المؤشرات |
|---|---|
| رئيس الجامعة | الطلاب النشطون، المتقدمون، المقبولون، التحصيل، البرامج، الأحرم، مؤشرات الأداء |
| الإدارة الأكاديمية | التسجيل حسب البرنامج، حجم الشعب، اكتمال النتائج، النجاح والتعثر، التخرج |
| مدير الحرم | القاعات، الصيانة، الخدمات، الطلبات المتأخرة، الموظفون التشغيليون في نطاقه |
| العميد | طلاب الكلية، الأقسام، الشعب، نتائج المقررات، عبء التدريس |
| رئيس القسم | المقررات والشعب والمدرسون والدرجات المطلوب تسليمها |
| القبول | الطلبات حسب الحالة، النواقص، التحويل إلى طالب، وقت المعالجة |
| المالية | الاستحقاقات والتحصيل والأرصدة والمتأخرات والمطابقة |
| الطالب | الجدول، الإشعارات، المهام، النتائج المنشورة، الرسوم المستحقة |
| عضو هيئة التدريس | الشعب والحضور والدرجات المعلقة |

## التقارير التشغيلية
- المتقدمون حسب دورة القبول والبرنامج والحالة.
- الطلبات الناقصة والمعلقة ومدة معالجتها.
- المقبولون الذين لم يستكملوا التسجيل.
- الطلاب النشطون حسب الحرم والكلية والقسم والبرنامج والدفعة.
- تاريخ حالات الطالب وقراراته.
- التسجيل حسب المقرر والشعبة والسعة.
- تعارضات الجدول والقاعات.
- الحضور والغياب وفق اللائحة.
- الدرجات غير المسلمة وغير المعتمدة.
- السجل الأكاديمي وكشف الدرجات الرسمي.
- المتوقع تخرجهم والنواقص.
- كشف حساب الطالب والتحصيل والمتأخرات.
- حركة الصندوق والفروقات والمطابقة.
- تكليفات المدرسين والنصاب إن اعتمدت قواعده.
- بلاغات الصيانة وزمن الحل وإشغال القاعات.
- طلبات الخدمات حسب النوع والحالة ومدة الإنجاز.

## التحليلات
- وصفي: ماذا حدث؟ الأعداد والمجاميع والاتجاهات.
- تشخيصي: أين التأخير أو التعثر؟ تحليل مجزأ حسب البرنامج والمقرر والفترة.
- تنبؤي: لاحقاً بعد توفر بيانات تاريخية كافية ومقيسة؛ لا تعرض التوقع كحقيقة.
- توجيهي: توصية تشغيلية تتضمن المشكلة والدليل والافتراضات والثقة والأثر وموافقة بشرية.

لا تبدأ تعلم الآلة قبل توافر تاريخ كافٍ وجودة بيانات وتعريفات مؤشرات معتمدة ومراقبة لانحياز النتائج.

## التصدير
PDF للوثائق والطباعة الرسمية؛ XLSX/CSV للتحليل. حد للصفوف الكبيرة ومهام خلفية، وتسجيل المستخدم والفلاتر والوقت في التصدير الحساس. لا SQL حر للمستخدم.

# 11. الاختبار وضمان الجودة ومعايير القبول

## مستويات الاختبار
1. Unit لقواعد الحساب والحالات.
2. Feature/Integration للطلبات وقاعدة البيانات والصلاحيات والمعاملات.
3. Browser/E2E لمسارات المستخدم الكاملة.
4. Security للصلاحيات الأفقية والرأسية والملفات والجلسات وIDOR.
5. Data integrity للتكرار والمفاتيح والمعاملات والاستعادة.
6. Performance وفق عدد المستخدمين المتزامنين المعتمد، لا عدد الطلاب فقط.
7. UAT من موظفي القبول والتسجيل والمالية والأحرم والعمداء.
8. Disaster recovery لاختبار استعادة نسخة حقيقية في بيئة معزولة.

## اختبارات لا بد منها
**الصلاحيات:** موظف حرم A لا يصل إلى حرم B بتغيير الرابط؛ مدير الحرم لا يغير نتيجة أو رسوماً؛ المدرس يرى شعبه فقط؛ التفويض ينتهي تلقائياً.

**القبول:** إرسال مزدوج بسبب انقطاع الشبكة لا يكرر الطلب؛ الطلب الناقص يعود للمتقدم؛ القبول غير المعتمد لا ينشئ طالباً؛ إعادة تحويل المتقدم لا تنشئ سجلاً ثانياً.

**الأكاديمية:** طالب خطة V1 يبقى عليها بعد نشر V2؛ المقرر مشترك دون تكرار؛ المتطلب السابق يطبق؛ لا تتجاوز السعة؛ النتائج لا تنشر قبل الاعتماد؛ تعديل نتيجة منشورة موثق بالقيم السابقة والجديدة.

**الجدولة:** منع تعارض القاعة والمدرس؛ القاعة المعطلة لا تحجز؛ تغيير الجدول يبلغ الأطراف ويحفظ التاريخ.

**المالية:** تكرار طلب الدفع أو webhook لا يكرر القبض؛ الرد مرتبط بالأصل؛ فشل الطباعة لا يلغي الدفع؛ غير المالي لا يرى كشف الحساب.

**التقارير:** لوحة الحرم تطابق تقرير التفاصيل؛ لا تصدير خارج النطاق؛ المسودات لا تدخل تقارير المعتمد إلا إذا صرح التقرير بذلك.

## معايير القبول
- كل متطلب له ID ومالك وقصة/سيناريو واختبار قبول.
- لا تعتبر الصفحة مكتملة وحدها؛ يجب اختبار قاعدة العمل والصلاحية والتدقيق.
- كل نموذج له تحقق خادمي ورسائل عربية.
- العمليات الحرجة قابلة لإعادة المحاولة دون تكرار.
- كل تقرير له مصدر وتعريف وتطابق.
- لا عيوب Critical/High مفتوحة قبل الإنتاج.

## الأداء
لا يمكن ضمان 5,000 طالب من العدد المسجل فقط؛ التزامن وحجم الملفات والتقارير أهم. تعتمد الجامعة سيناريو حمل، ثم يقاس على بيئة قريبة من الإنتاج. هدف أولي للمراجعة وليس ضماناً: P95 للقراءة المعتادة ≤2.5 ثانية والكتابة المعتادة ≤3.5 ثانية، باستثناء التقارير الثقيلة ورفع الملفات؛ يعاد ضبط الهدف بعد خط أساس.

## بوابة الإطلاق
اعتماد السياسات؛ UAT؛ HTTPS؛ نسخ واستعادة مختبرة؛ إغلاق العيوب الحرجة والعالية؛ تدريب؛ بيانات مرجعية معتمدة؛ اختبار أدوار ونطاقات؛ اختبار الطباعة العربية؛ خطة رجوع ودعم.

# 12. بيئات التطوير والنشر والتشغيل

## البيئات
| البيئة | الاستخدام | البيانات |
|---|---|---|
| Local | جهاز المطور/XAMPP | اصطناعية فقط |
| Development | تكامل المطورين | اصطناعية |
| Staging/UAT | محاكاة الإنتاج والقبول | اختبار أو بيانات منزوعة الهوية بموافقة |
| Production | التشغيل الفعلي | بيانات الجامعة الحقيقية |

## XAMPP
XAMPP للتطوير المحلي وليس للإنتاج المتاح على الإنترنت. افحص PHP CLI وPHP Apache وMySQL؛ لا تسمح باختلاف نسخة PHP التي يستخدمها Composer عن نسخة تشغيل التطبيق. إذا استخدمت `php artisan serve` فالمهم PHP CLI المتوافق وقاعدة MySQL العاملة. لا يلزم وضع المشروع في `htdocs` عند تشغيل خادم Laravel المحلي.

## إنتاج موصى به
- Linux LTS مدعوم ومحدث.
- Nginx أو خادم ويب مناسب + PHP-FPM متوافق.
- MySQL 8.4 LTS على خادم منفصل أو عقدة مؤمنة.
- HTTPS/TLS.
- تخزين ملفات خاص خارج web root.
- Redis/cache/queue حسب قياس الحمل.
- Queue workers وScheduler مستمران.
- مراقبة موارد الخادم وقاعدة البيانات والمهام والأخطاء.
- فصل إدارة الخوادم عن شبكة المستخدمين قدر الإمكان.

## أحرم الجامعة والاتصال
قاعدة مركزية وخدمة تطبيق مركزية أو عالية التوافر، وشبكة آمنة تربط الأحرم. انقطاع الإنترنت الخارجي يختلف عن انقطاع WAN/LAN أو تعطل الخادم. يوصى بخط ربط أساسي واحتياطي حسب الميزانية. لا تنشئ قاعدة قابلة للكتابة بكل حرم دون تصميم تزامن مثبت؛ فهذا يعرض التسجيل والدرجات والمدفوعات للتعارض.

## النشر
1. إصدار ثابت من Git/CI.
2. نسخة احتياطية قبل migration.
3. صيانة عند الحاجة.
4. تثبيت dependencies من lock files.
5. تنفيذ migrations بعد مراجعة الأثر.
6. بناء الواجهة وتحديث cache وفق Laravel.
7. إعادة تشغيل workers.
8. فحص health check ومسارات أساسية.
9. إخراج الصيانة ومراقبة التطبيق.
10. توثيق الإصدار والمنفذ والوقت.

## النسخ الاحتياطي
نسخ DB والملفات بصورة متناسقة، تشفير، نسخة خارج الخادم الأساسي، احتفاظ يومي/أسبوعي/شهري وفق السياسة، واختبار استعادة دوري. تحديد RPO/RTO بعد اتفاق الجامعة وقياس قدرة الاستعادة؛ لا تخمين.

## مراقبة التشغيل
CPU/RAM/Disk، اتصالات MySQL والاستعلامات البطيئة، تراكم Queue والمهام الفاشلة، HTTP 5xx، زمن الاستجابة، محاولات الدخول، حجم النسخ، صلاحية الشهادات. إجراءات يومية لفحص النسخ والخدمات والأخطاء والدعم.

## قرارات تفصيلية يجب إغلاقها قبل اعتماد ERD الفعلي

### 1. هوية الشخص والمعرفات الرسمية
- **السؤال:** ما البيانات الرسمية التي تميز الشخص؟ وهل يمكن أن يحمل الشخص معرفاً جامعياً ومعرفاً وظيفياً في الوقت نفسه؟
- **التوصية:** سجل شخص مركزي واحد، ومعرفات متعددة ذات نوع وقيمة وجهة إصدار وتواريخ، مع عدم استخدام الرقم الجامعي مفتاحاً أساسياً.
- **المالك:** القبول والتسجيل والموارد البشرية والشؤون القانونية.
- **الأثر:** `people`, `person_identifiers`, `students`, `employees` وسياسات منع التكرار.

### 2. الدراسة المتزامنة أو المتتابعة في أكثر من برنامج
- **السؤال:** هل يسمح للطالب بقيدين أكاديميين نشطين في الوقت نفسه؟ وما قواعد الرسوم والجدول والتخرج؟
- **التوصية:** تصميم علاقة التحاق مستقلة بين الطالب والبرنامج والفترة، وعدم افتراض أن الطالب له برنامج واحد طوال حياته؛ تفعيل تعدد القيد وفق اللائحة فقط.
- **المالك:** الشؤون الأكاديمية والقبول والمالية.
- **الأثر:** `student_program_enrollments`, `student_plan_assignments`, التسجيل والرسوم.

### 3. نظام الساعات أو الوحدات أو النظام السنوي
- **السؤال:** ما تعريف العبء الأكاديمي، والساعة المعتمدة، والمتطلبات والسنة الدراسية؟
- **التوصية:** إبقاء وحدات القياس والساعات في توصيف المقرر والخطة، وعدم اختراع قاعدة تحويل أو حد تسجيل قبل اعتماد النظام الأكاديمي.
- **المالك:** الشؤون الأكاديمية ومجالس الكليات.
- **الأثر:** الخطط، حساب العبء، التسجيل، المعدل والتخرج.

### 4. التبعية الرسمية للأقسام والوحدات
- **السؤال:** هل يتبع كل قسم كلية واحدة دائماً؟ وكيف تُسجل إعادة الهيكلة أو نقل القسم؟
- **التوصية:** تبعية واحدة فعالة للقسم في فترة زمنية محددة، مع سجل تاريخي للتغييرات وعدم إعادة كتابة الماضي.
- **المالك:** مجلس الجامعة والموارد البشرية والشؤون الأكاديمية.
- **الأثر:** `departments`, `organizational_units`, تعيينات الموظفين والتقارير التاريخية.

### 5. ملكية المقرر ومشاركته
- **السؤال:** من يملك توصيف المقرر عند تقديمه لأكثر من برنامج أو كلية؟
- **التوصية:** كتالوج موحد للمقرر، مع جهة أكاديمية مسؤولة أساسية، وعلاقات استخدام ومشاركة، وإصدارات للتوصيف. لا يُنسخ المقرر لمجرد اختلاف البرنامج.
- **المالك:** الشؤون الأكاديمية والأقسام ومجالس الكليات.
- **الأثر:** `courses`, `course_versions`, `study_plan_courses`, تكليفات التدريس.

### 6. التقديرات والمعدل والنجاح والرسوب
- **السؤال:** ما سلم التقدير، طريقة احتساب المعدل، التقريب، الأوزان، الإعادة، والتحسين؟
- **التوصية:** قواعد قابلة للإصدار حسب اللائحة والفترة، مع حفظ النتيجة المعتمدة تاريخياً وعدم إعادة احتسابها بصمت بعد تغيير السياسة.
- **المالك:** المجالس الأكاديمية والجهة المخولة باعتماد النتائج.
- **الأثر:** التقييم والنتائج وكشف الدرجات وفحص التخرج.

### 7. معادلة المقررات والتحويل
- **السؤال:** ما الوثائق ومعايير المطابقة والحدود والجهة التي تعتمد المعادلة؟
- **التوصية:** عملية مستقلة بقرار موثق يربط المقرر السابق بالمقرر المعادل، مع حفظ المصدر والساعات/الوحدات والنتيجة وسبب القرار.
- **المالك:** لجنة المعادلات والشؤون الأكاديمية.
- **الأثر:** `student_course_equivalencies`, سجل الطالب، الخطة والتخرج.

### 8. العملة والرسوم والضرائب والتقسيط
- **السؤال:** ما العملات المعتمدة، العملة المرجعية، سعر الصرف، توقيت تثبيته، الضرائب، المنح، الاسترداد والتسويات؟
- **التوصية:** تسجيل مبلغ كل حركة مع العملة وسعر الصرف المرجعي عند انطباقه، وعدم تعديل الفواتير التاريخية عند تغيير سياسة الرسوم. لا تفترض ضريبة أو نسبة أو عملة دون اعتماد.
- **المالك:** الإدارة المالية والإدارة العليا والمستشار القانوني عند الحاجة.
- **الأثر:** الفواتير والتحصيل وكشوف الحساب والتقارير والمطابقة.

### 9. الاحتفاظ بالبيانات والوثائق والخصوصية
- **السؤال:** ما مدة حفظ ملفات المتقدمين والطلاب والموظفين والسجلات المالية والأكاديمية؟ ومن يحق له الاطلاع أو طلب نسخة؟
- **التوصية:** تصنيف البيانات، تحديد مدة احتفاظ لكل فئة، سجل تنزيل وتعديل، تخزين خاص للمرفقات، وسياسة إتلاف أو إخفاء هوية معتمدة قانونياً.
- **المالك:** الإدارة والمستشار القانوني وتقنية المعلومات.
- **الأثر:** الأمن، الأرشفة، النسخ الاحتياطي، بوابة التقارير وحقوق الوصول.

## افتراضات لا تتحول إلى حقائق
- الأعداد والأسماء النهائية للأحرم والكليات والأقسام والبرامج غير معروفة.
- لا توجد رسوم أو شروط قبول أو تقويم نهائي معتمد ضمن المعطيات الحالية.
- لا نفترض نظام الساعات أو الوحدات قبل اعتماد الشؤون الأكاديمية.
- لا نستنتج عدد المستخدمين المتزامنين من عدد الطلاب فقط؛ يجب قياسه أو تقديره تشغيلياً.
- الماجستير والدكتوراه ضمن الرؤية المستقبلية، لكن تفاصيلهما تنتظر اللوائح المعتمدة.
- دعم البرامج المشتركة في التصميم لا يعني أن الجامعة قررت إطلاق برنامج مشترك الآن.

## آلية إغلاق كل بند
لكل بند معلق يجب تسجيل: رقم القرار، المالك، المرجع الرسمي، نص القرار أو القيمة، جهة الاعتماد، تاريخ السريان، الوحدات المتأثرة، خطة ترحيل إن وجدت، وحالات الاختبار الناتجة. يبقى الإعداد غير مفعل أو يستخدم وضعاً يمنع العملية إلى حين الاعتماد؛ لا يخترع المطور قيمة افتراضية في سياسة مؤثرة.

# 15. دليل المطور والتسليم

## التسمية
PHP classes `StudlyCase`، methods `camelCase`، جداول وأعمدة `snake_case`، Routes مثل `admissions.applications.index`، Permissions مثل `finance.payment.reverse`. Enum codes ثابتة بالإنجليزية والترجمة في ملفات اللغة. رموز العمل مثل student_no مستقلة عن المفتاح الأساسي.

## قواعد قاعدة البيانات
- Migration لكل تغيير مستقل.
- لا تعدل قاعدة الإنتاج يدوياً في phpMyAdmin؛ المخطط في migrations.
- راجع تأثير migration على الفهارس والقفل والجداول الكبيرة.
- استخدم FK/unique/index؛ لا cascade delete على بيانات مالية/أكاديمية معتمدة.
- التحقق في DB ضروري للتفرد والتزامن بجانب Laravel validation.

## قواعد Laravel
- Controllers رفيعة؛ لا تضع منطق الأعمال متعدد الخطوات في Blade أو Livewire component.
- كل إدخال يمر عبر Form Request/Validator.
- كل مورد يمر عبر Policy ونطاق استعلام.
- كل عملية حساسة لها transaction وidempotency عند إعادة المحاولة.
- Jobs قابلة لإعادة المحاولة دون مضاعفة الأثر.
- لا تستخدم `env()` خارج config.
- لا ترفع `.env` أو أسراراً أو بيانات حقيقية إلى Git.

## مكونات تسليم كل ميزة
متطلب/تصميم، migration، model، validation، policy، action/service، route/UI، tests، ترجمة، تحديث الوثائق، نتيجة اختبار.

## مراجعة Pull Request
- تغطية حالات النجاح والفشل والاستثناء.
- تحقق الصلاحية والنطاق في الخادم.
- منع التكرار والتعارض.
- تدقيق العملية الحساسة.
- معاملة قابلة للاستئناف/إعادة المحاولة بأمان.
- واجهة RTL مفهومة وحالات فراغ وخطأ.
- الاختبارات ناجحة والوثائق/ERD محدثة.

## حزمة التسليم
مصدر Git مع Tag، migrations/seeders، قائمة routes والصلاحيات، وصف العمليات والشاشات، اختبارات، تعليمات تثبيت/ترقية/تراجع، دليل مستخدم وتشغيل، وسجل تغييرات.
